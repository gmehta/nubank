Nubank Engineering Ontology

One context layer under every code-review agent. A structural tier that is deterministic and identical for every repo, a concept tier each squad fills with its own domain, and the functions and actions an agent calls on top — the same four primitives Palantir's ontology uses (object, link, function, action), applied to code instead of enterprise data.

Structural tier — tree-sitter, no LLM, ms-fresh Concept tier — LLM-enriched, squad-owned Functions — read, compute Actions — write, validated, audited

What happens when a PR opens against nubank/nodely

Structural: fixed schema, zero variation

Repository, namespace, function, type, test, interface, PR, CI, deploy — parsed deterministically from every repo, Clojure or Go or Dart alike. The platform team owns the schema; nobody customizes it. Regenerated in milliseconds, git-ignored like node_modules.

Concept: fixed schema, high variation

Service, capability, domain concept, invariant, control, standard, squad, incident, data class. The shape is the same everywhere; the content is each squad's own vocabulary, LLM-drafted from source and human-corrected, cached by content hash.

Functions read, actions write

Functions compute over both tiers and never mutate. Actions change state only after validation — owner exists, approver named, no live callers — and every execution lands in an audit log. Fail closed, never open.

Actions

Validated write-backs. Each has preconditions the platform checks before execution, a side effect, and an audit entry. An agent can propose any of them; the validation decides whether it runs.
